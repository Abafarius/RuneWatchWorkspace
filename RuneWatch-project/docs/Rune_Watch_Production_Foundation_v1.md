# Rune Watch — Production Foundation v1.0

**27 ноября 2026 · рабочий стандарт для утверждения · Windows / Steam · соло-разработка с ИИ**

Назначение: объяснить, как получить коммерчески пригодную игру без навыков художника, 3D-моделера, аниматора или композитора. Это руководство по производству, а не новая сборка. В комплекте — шаблоны учёта ассетов, задач, приёмки, генерации и архитектурных решений. Реальные модели и музыка пока не закуплены, не скачаны и не протестированы.

## 1. Решения и границы

Актуальное решение автора: Living Voxel Fantasy — настоящая 3D-диорама с кубическими фигурками, не пиксельные спрайты; минимум ручного управления, максимум синергий. Основа — один игровой экран, автоматическая армия, механический рычаг и барабаны, поглощение и развитие бойцов, награды и пассивные эффекты. Мимир — одушевлённый механизм и рассказчик, наследование — потенциальная уникальная механика. Мимир комментирует редкие события без обязательных диалогов. Смешанные эффекты создают новые билды, а не дополнительную работу для игрока. Вращения только за игровые ресурсы, никаких платных вращений за реальные деньги.

### Иерархия документов

- Последние решения автора в обсуждении и утверждённые ADR определяют направление.
- Этот документ задаёт производство. GDD v2 остаётся историческим источником идей: его ручная расстановка, редактор барабанов, тактическая сетка и обязательная карта не являются актуальными требованиями.
- Art Bible v1 (26.11.2026) сохраняет правила контраста, палитры, идентичности Мимира, доступности, тестирования и лицензирования. Пиксельные размеры 32×32, холст 640×360, nearest и целочисленное масштабирование **не действуют** для нового 3D-мира. Их заменяет раздел 3 настоящего документа.
- Первоначальный производственный план: лимит 450 000 ₸, ориентир 12 часов в неделю, платная игра и бесплатное демо. Сроки и смета требуют пересмотра после Style Slice. Старые HTML-сборки до alpha.2 — архив экспериментов, не основной продукт. Переносим правила, сценарии и тестовые идеи, не портируем интерфейс строка в строку.
- GDD 3.0 и Art Bible 2.0 ещё предстоит утвердить после проверки визуального эталона. Не считать этот документ подтверждением всех ранее предложенных классов, боссов или реликвий.

## 2. Как работаем вдвоём

Автор отвечает за выбор, установку программ, ручную проверку, локальные файлы, бюджет и права. ИИ готовит код, спецификации, тесты, референсы и инструкции, помогает разбирать скриншоты/логи, при доступности инструментов создаёт исходники и ассеты. Не требуется учить весь Blender или становиться профессиональным художником. Учимся только операциям, необходимым текущей задаче.

Каждая поставка содержит: цель, предпосылки, короткое объяснение терминов, шаги Windows с путями и названиями элементов UI, ожидаемый результат, способ отката, исходники/патч, тесты, ограничения, обновлённые документы, предложение названия Git-коммита. Пользователь выполняет инструкции и присылает результат. ИИ не может сам проверить локальный ПК, купленные файлы или качество живого плейтеста без предоставленных данных. Не заявлять, что что-либо проверено, если была только генерация или просмотр превью.

Порядок: постановка задачи → небольшой эксперимент → сравнение с эталоном → реализация → проверка → приёмка автором → коммит. Одновременно одна основная задача. Не менять движок, арт-стиль и ключевые правила в одном патче. Непринятый ассет не становится зависимостью всей игры.

## 3. Visual Style Guide (переход на 3D)

### 3.1. Арт-направление

Ключевые слова: collectible fantasy miniature, chunky voxel, living tabletop diorama, warm bronze, moss, twilight, readable silhouettes, playful physical motion. Не Minecraft, не фотореализм, не сглаженные low-poly персонажи вперемешку с воксельными. Изображения ИИ — только концепты до тех пор, пока не получены пригодные для движка модели. Не утверждать стиль по одному красивому рендеру.

| Параметр | Рабочий эталон для Style Slice |
|---|---|
| Камера | Orthographic, наклон вниз ~30–40°, поворот к полю ~20–35°; фиксированная, без свободного вращения |
| Композиция | Мимир слева ~25–30% ширины, свободное поле справа, HUD поверх сцены; важные элементы не перекрывают фигуры |
| Масштаб | 1 Godot unit = 1 м; обычный воин 1,2 м высотой, основание ~0,6 м; босс 2–3× выше |
| Модуль | Рабочий шаг вокселя 0,075 м (16 шагов на рост 1,2 м); у крупных объектов допустим кратный шаг |
| Площадка | Около 12×7 м игрового пространства, уточняется по камере; без визуальной сетки |
| Персонажи | Крупная голова, короткие конечности, выразительное оружие; силуэт виден при масштабе полного экрана |
| Материалы | Матовые, с ограниченным металлическим блеском и локальным emissive у магии; без фотореалистичных PBR-текстур |
| Свет | Один направленный тёплый ключевой свет, мягкое окружение, холодный заполняющий тон; тени не закрывают силуэты |
| Фон | Декоративный и менее контрастный, чем бой; одно узнаваемое место действия |
| HUD | Нативный 2D CanvasLayer/Control; RU/EN, текст не меньше ~16 px при 720p (проверить на реальном окне) |
| Доступность | Различать стихии по формам, врагов по силуэтам и маркерам; настройки вспышек, тряски, громкости и масштаба |

Все числа — начальная спецификация, не измеренные требования. Подтверждаем на первых 2–3 моделях. Единый шаг вокселя важнее числа полигонов. В отличие от 2D, рендерим 3D в разрешении окна или через настраиваемый масштаб рендера, не растягиваем кадр 640×360.

### 3.3. Мимир — якорь бренда

Оригинальная модель: низкий массивный бронзовый корпус, две подвижные светящиеся брови/глаза, три барабана с тремя видимыми позициями, крупный красный рычаг справа, руническая эмблема. Сначала корпус без дорогой детализации, отдельные mesh/узлы lever, eye_left, eye_right, reel_0..2. Pivot рычага в шарнире. Рисуем/генерируем концепт, затем собираем геометрию из блоков в MagicaVoxel, Blender или процедурным скриптом; подвижные элементы отделяем. Барабаны можно отрисовать на SubViewportTexture или собрать из отдельных поверхностей; проверяем читаемость, а не симулируем сложный механический цилиндр. Реплики текстовые, короткие; кулдаун, повторение не чаще заданной частоты, отключение в настройках. Без живого LLM в игре на старте.

## 4. Asset Strategy: готовое, генерируемое, собственное

Ориентир 80/20 — принцип распределения усилий, не фиксированная квота. Главное — один совместимый набор основы и ограниченная кастомизация. Покупной красивый, но несовместимый пак обходится дороже простого общего набора.

| Категория | Основной путь | Что делаем сами / с ИИ |
|---|---|---|
| Мимир | Оригинальная модульная модель | концепт, простая блочная геометрия, процедурные движения |
| Бойцы и враги | Один основной воксельный набор с редактируемыми моделями | перекраска, оружие, части тела, недостающие роли |
| Окружение | Один согласованный набор руин/растительности | композиция диорамы, свет, повторяемые биомы |
| Анимации | Общие клипы набора, либо жёсткие части тела | idle, удар, отскок, смерть, рычаг через AnimationPlayer/Tween |
| Мутации | Модульные аксессуары | огненное оружие, ледяные кристаллы, костяная маска |
| VFX | Godot particles, простые меши | кубики, вспышки, магические снаряды, взрывы |
| UI и руны | Собственные иконки/рамки, разрешённый шрифт | генерация концептов, отбор, чистка, единый размер |
| Музыка | Лицензированные петли или AI-композиции с правами | промпты, нарезка, сведение |
| SFX | CC0/коммерческие паки | многослойные щелчки, магия и голосовые звуки |
| Локализация | Собственные тексты, помощь ИИ | вычитка RU/EN, проверка в интерфейсе |
| Маркетинг | Собственные игровые кадры | трейлер, capsule art после визуальной приёмки |

### 4.2. Ворота выбора пака

Оценка 0–2 по каждому из 6 критериев: соответствие силуэту и шагу вокселя, палитра/материалы, редактируемые исходники, доступность отдельных частей/рига, качество импорта, стоимость интеграции. Цель ≥9/12 и никаких нулей по формату и модульности для основной семьи. Лицензия — обязательный отдельный pass/fail; никакой высокий балл не компенсирует её отсутствие. Тестируем 1 воина и 1 мага в одной камере, затем ледяную мутацию; не покупаем набор из 100 моделей до теста. Если не нашли подходящий пак, делаем простой собственный блочный kit, не смешиваем несовместимые модели.

## 6. Asset pipeline — от идеи до игры

### 6.1. Общий маршрут

Brief → подбор/генерация → проверка прав → карантин исходников → нормализация в Blender → GLB → сцена-обёртка Godot → проверка в эталонном кадре → реестр → приёмка → коммит. Храним лицензию и оригинальный архив отдельно; не кладём купленные сырые ассеты в публичный Git и не пересылаем их ИИ, если договор запрещает передачу третьим лицам. ИИ-провайдеру не передаём купленную модель или чужой референс без соответствующего права.

### 6.2. Форматы и термины

- Mesh — геометрия; material — цвет/блеск/эмиссия; texture — изображение, используемое материалом. Pivot — точка вращения/опоры. Rig — система суставов, двигающих части модели. Animation clip — сохранённая последовательность движений. GLB — бинарный glTF-контейнер, удобный для импорта моделей, материалов и анимаций в Godot. Файл .vox — исходник вокселей, не готовый персонаж Godot; OBJ — статическая геометрия без скелетной анимации.
- В Blender: File → Import → соответствующий формат (OBJ, glTF или FBX). Для .vox сначала экспорт OBJ из MagicaVoxel; сохранить OBJ/MTL и PNG рядом. Проверить видимые материалы. Нормализовать масштаб в Object Mode, origin на земле, forward согласовать с эталоном (в Godot модель смотрит вдоль -Z). Для статического объекта Ctrl+A → Rotation & Scale; для ригов не применять трансформации вслепую, проверять клипы после изменений.
- Если модель — отдельные блоки, не создавать по Node3D на каждый воксель. Объединяем статические куски по материалу или функциональной части, избегаем внутренних граней, но не сливаем подвижные руки с корпусом. Для текстурированной модели не удаляем материалы случайно.
- File → Export → glTF 2.0, формат GLB; экспорт выбранной модели, её нужных материалов и клипов; проверить, что нужные текстуры включены. Повторно импортировать в Blender или Godot для контроля. Сохраняем .blend как исходник и .glb как runtime-артефакт. [Godot: форматы](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html).
- В Godot копируем GLB в assets/models/; FileSystem автоматически импортирует. Создаём собственную сцену UnitView.tscn с корневым Node3D, дочерней инстанцией модели и узлами точек крепления. Не редактируем импортированные внутренности напрямую, иначе повторный импорт затрёт изменения. Для точечных настроек используем Import/Advanced или inherited scene.

### 6.3. Анимации

Два пути. Для жёстких воксельных частей тела (предпочтение на старте): отдельные pivots головы, корпуса, рук и ног, AnimationPlayer анимирует локальные трансформации; Tween для отдачи и рычага. Для набора с полноценным общим скелетом: импорт анимационных клипов, AnimationPlayer, затем при необходимости AnimationTree. Mixamo — только после проверки совместимого гуманоидного рига, иначе придётся ретаргетить и чинить веса. Не смешивать пути в одном персонаже без причины.

Минимум клипов: idle (петля 1,5–2 с), walk (0,6–1 с), attack (0,35–0,8 с), hit (0,08–0,15 с), death (0,4–0,9 с), cast (может быть вариацией attack). Это визуальные ориентиры, не тайминг симуляции. Движение по миру и факт удара определяет логика, не событие анимации. Мутации привязываем к socket_head/back/weapon/body. Визуальный тест: все клипы с 3 мутациями; оружие не проходит сквозь тело настолько, что это бросается в глаза; нет скачка при переходе idle/walk; смерть не оставляет невидимый коллайдер. Смерть — ограниченный пул косметических кубиков, не десятки постоянных RigidBody3D на каждого воина.

### 6.4. AI 3D: эксперимент, не конвейер по умолчанию

Генерация 2D-концептов полезна для Мимира, классов и UI; текст/изображение → 3D часто выдаёт не настоящий воксель, а неровную плотную сетку, запечённые тени и слитые части. Пробуем один результат, проверяем топологию, материалы, pivot и редактируемость, затем сравниваем время исправления с ручной сборкой простых кубов. Отбрасываем плохой результат, не покупаем подписку на несколько генераторов. Не просим «в стиле конкретного автора/игры»; описываем форму, палитру, масштаб. Для оригинальных блочных моделей можно генерировать Blender Python-скрипты с геометрией; автор запускает их локально после просмотра, сохраняет .blend и проверяет результат. Промпты в templates/PROMPTS.md.

## 8. Музыка и звук

Арт-дирекшн звука: уютное приключенческое фэнтези, дерево, бронза и механика; выразительные звуки наград, но не звуковая атака при 80 бойцах. Музыка спокойная, инструментальная, 1–2 минуты без резких вокальных фраз; бой добавляет энергию через SFX, музыка не обязана постоянно переключаться. На Style Slice один луп по желанию. Вначале тестируем звуковое ядро: рычаг → треск вращения → три щелчка с небольшим изменением pitch → джекпот/призыв. Основной UI тихий. Не делать звук каждого удара одинаковой громкости; лимит одновременно играющих однотипных эффектов, короткий cooldown, вариация высоты на несколько процентов.

Audacity: File → Import → Audio; выделить нужный участок, обрезать лишнее, применить короткие fade in/out против щелчков, проверить отсутствие клиппинга; экспорт WAV PCM 16-bit, 44.1 или 48 kHz для SFX, моно при отсутствии пространственной информации. Музыка OGG (или исходный WAV в source library), стерео, проверить стык вручную минимум 10 циклов. Godot AudioStreamPlayer/AudioStreamPlayer3D; buses Master, Music, SFX, UI, Voice, регулировки сохраняются. Не добавлять все звуки сразу; прослушивать на тихой и обычной громкости.

Если используем Suno: не выдаём коммерческое право за исключительное авторское право. Сохраняем prompt, дату, ID трека, план подписки и доказательство условий генерации/скачивания. Проверяем отсутствие имитации конкретного исполнителя и подозрительно похожих мелодий. Бесплатный трек без коммерческого разрешения — исключительно локальный временный материал, исключить из дистрибутива. Альтернатива — CC0 музыка или купленный game music pack с разрешённым синхронным использованием в игре. Промпты см. приложение.

## 10. Архитектура и структура файлов

Один приватный локальный репозиторий для Godot (новый или отдельная ветка; старый HTML пометить архивным тегом). Предпочтение отдельный репозиторий rune-watch-godot, чтобы не смешивать старую веб-архитектуру с новой. Если выбираешь ветку — сначала коммит/резервная копия старого проекта. Не удалять .git. Сторонние исходники и доказательства лицензий храним вне экспортируемого проекта, с отдельным бэкапом; локальный Git не является единственной резервной копией.

```text
RuneWatchWorkspace/
  source_library/           # вне runtime и публичных репозиториев
    originals/ licenses/ generated/ blender/ audio/
  rune-watch-godot/          # Git root, project.godot здесь
    project.godot
    scenes/                 # main, world, mimir, units, hud, lab
    scripts/                # domain, effects, presentation, persistence
    data/                   # .tres или JSON; постоянные ID
    assets/                 # только одобренные runtime-файлы
      models/ materials/ textures/ animations/ audio/ ui/
    tests/
    docs/                   # GDD, ART_BIBLE, PRODUCTION, ADR, STATUS
    tools/                  # проверки, сборка, отчёты
    .gitignore
    README.md
    CHANGELOG.md
  builds/                   # экспорт Windows, отчёт, скриншоты
```

Игнорируем .godot/, локальные credentials, кэши, сборки и временные файлы; не игнорируем Godot .uid sidecars, необходимые проекту. Не тащить весь скачанный пак в runtime. Проверить export filters и лицензионный состав. Если понадобится Git LFS при больших бинарниках, сначала согласовать резервирование и переносимость; пока достаточно малых GLB.

Движок: RunState (seed, ресурсы, фаза) → RuneEngine (результат спина) → ArmyEngine (призыв/поглощение) → CombatEngine (фиксированный шаг времени) → EffectEngine (очередь событий) → Presentation (модели/эффекты/звук/HUD). UI вызывает команды; презентация не определяет урон. Случайность симуляции отдельно от визуальных частиц. Один источник состояния, тестирование seed. Физика стилизует удары, не определяет исход боя случайным отскоком. Лимит глубины и событий, ID источника/цепочки, дедупликация смерти, запрет бесконечного самовызова, лог при срабатывании защиты. Сильные конечные цепочки — цель, а не баг. Сохранения с версией и атомарной заменой — после ядра забега.

### Урок 1: начать сегодня

1. На личном Windows ПК скачай Godot 4 Standard (x86_64) с официальной страницы. Распакуй в `C:\Dev\Tools\Godot\` (путь примерный), запусти editor exe. Не устанавливай .NET и export templates до первой необходимости.
2. Создай `C:\Dev\RuneWatchWorkspace\`. В Project Manager → Create / New Project, имя Rune Watch, путь `C:\Dev\RuneWatchWorkspace\rune-watch-godot`, Renderer: Compatibility, Version Control Metadata: Git, если есть такой выбор. Create & Edit. Если меню отличается — пришли скриншот и номер версии, не ищи случайный аналог.
3. В редакторе выбери 3D Scene, корневой Node3D переименуй в `Main`, сохрани Ctrl+S как `main.tscn` в корне на первом уроке. Позже перенесём в scenes/ средствами редактора.
4. Выдели Main → Add Child Node (Ctrl+A в панели Scene) → MeshInstance3D. В Inspector → Mesh → New BoxMesh. Назови Ground; Transform → Scale X=8, Y=0.2, Z=5; Position Y=-0.1. Второй MeshInstance3D, New BoxMesh, назови TestUnit, Position Y=0.5 (куб 1 м на земле).
5. Добавь DirectionalLight3D; Rotation Degrees X=-50, Y=-35; включи Shadow/Enabled. Добавь Camera3D, Position (9, 9, 12), Rotation Degrees (-31, 37, 0), Projection Orthogonal, Size 12, Current включён (углы приблизительные, подстрой если куб не в центре). Не нужно пока моделировать замок.
6. Нажми F6 — запустить текущую сцену. Должны быть видны площадка и освещённый куб. Если пусто, проверь, что камера текущая, куб имеет Mesh, камера смотрит на сцену, свет включён. F8 — остановить. F5 предложит главную сцену, выбери текущую.
7. В Project Settings → Display → Window проверь базовый размер 1280×720 (Viewport Width/Height и параметры окна, название зависит от версии). На уроке достаточно видимой сцены. Сохрани Ctrl+S.
8. GitHub Desktop → File → Add Local Repository, выбери папку проекта; если Git ещё нет, создай репозиторий через программу именно в папке проекта, без публикации. Проверь Changes: .godot/ не должна попасть в коммит. Коммит `chore: initialize Godot voxel workspace`. Скопируй руководство в docs/ и сделай отдельный коммит при необходимости.
9. Пришли скриншот сцены в Play и редактора с деревом Scene, версию Godot и указание, если возникла ошибка. Это критерий перехода к импорту первой модели. Не нужно скачивать платные ассеты, учить Blender, делать музыку или экспортировать игру сегодня.

Урок 2 (после результата): взять Quaternius RPG Character Pack, распаковать вне репозитория, проверить лицензию, выбрать одну модель и импортировать в Godot как учебную. При отсутствии GLB использовать FBX или конвертировать в Blender. Добавить в Main как дочернюю сцену, проверить высоту/ориентацию, открыть AnimationPlayer и проиграть idle/walk. Сравнить с коробочным тестом. Не считать этот low-poly ассет финальным воксельным стилем.

## 13. Quality Gate: как отличить продукт от набора ассетов

Оцениваем каждую сцену с фиксированной камеры, на нейтральном стенде и в настоящем игровом кадре. Сохраняем до/после. Субъективная оценка автором плюс измеримые проверки. Шаблон QUALITY_GATE.md используется на каждую поставку. Статусы planned → implemented → tested → accepted; accepted ставит автор после демонстрации. Технические проверки не заменяют плейтест.

- Визуал: без смешения несовместимых размеров, материалов и перспективы; 6 классов узнаются в сцене без подписей; проверяем слепым тестом у 3–5 человек, целевой ориентир 5/6 ролей; силуэты читаются, когда на поле много бойцов; все три мутации различимы. Если нет — исправить масштаб, силуэт, свет.
- UI: 1280×720, 1920×1080, 2560×1440, 4K и 16:10; не обрезается кириллица, рычаг виден и доступен, окно/полноэкранный режим не растягивает мир; редкие эффекты не закрывают кнопку паузы. Для первого S0 только 720p/1080p; полный набор к S4.
- Game feel: рычаг следует за мышью, отпускается без двойного спина, щелчки синхронизированы, 3 барабана останавливаются последовательно. Неполное движение можно отменить; доступна кнопка/клавиша. Автовращение не тратит ресурсы при выборе награды. Стопор и платные вращения не обязательны, решение о них после плейтеста. Не вводим задержки ради искусственного удержания игрока.
- Производительность: целевой минимум 60 FPS (16,67 мс на кадр), 80 активных персонажей, стресс 150, один согласованный минимальный ПК. Сначала измерить на личном ПК в release/exported build, 1080p, по 60 секунд на 20/80/150 бойцов после прогрева, записать среднее и p95 frame time, renderer, CPU/GPU, графику, число эффектов. Цель p95 ≤16,67 мс на 80 бойцах; стресс-тест обязан не падать, фиксируем фактический FPS, не обещаем 60. Дешёвые общие материалы, пулы, ограниченные частицы, нет rigidbody на каждый воксель; MultiMesh только там, где измерения оправдывают. Если есть лишь один мощный ПК, минимальные требования не подтверждены.
- Логика: одни и те же seed/команды дают одинаковый результат при ×1/×2/×4, паузе и пропуске; не допускаем двойное начисление, бесконечные триггеры, зависание при гибели. Сценарии поглощения, смены цели, цепной смерти, остановки авто при награде. S4 может использовать постановочное сражение, полноценная проверка логики в S5/S6.
- Права/дистрибуция: все shipped ассеты имеют разрешение, экспорт не включает исходные покупки, тестовые треки, личные данные. Windows-сборка запускается на втором ПК до публичного демо. Отмечать непроверенное явно.

## 14. Первая поставка и дальнейший порядок

Сегодня запускаем Урок 1 и проверяем скриншот. После этого S0.2 — импорт учебного персонажа и выбор основной воксельной семьи по критериям. Затем один эталонный кадр в Godot, а не очередная генерация рекламной картинки. В S1 сравниваем 2–3 модели в одинаковой композиции; только после подтверждения масштабируем контент.

Готовность этой поставки: подготовлен производственный стандарт и шаблоны. Код не изменён, готовых игровых ассетов в архиве нет. Необходимые решения автора: окончательный внешний вид воксельной семьи, допустимые расходы, камера и рендерер после практического теста. Пока придерживаемся нулевых расходов и минимального объёма. Никакие платные инструменты не являются условием старта.
